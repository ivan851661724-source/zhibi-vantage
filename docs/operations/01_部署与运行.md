# 知彼 Vantage 部署与运行

状态：运行操作说明。命令均在仓库根目录执行。当前服务、构建路径、端口和镜像版本以[编排文件](../../docker-compose.yml)、[后端镜像](../../Dockerfile)及[前端镜像](../../web/Dockerfile)为准；本文不自动授权部署或发送通知。整体结构见[整体架构规范](../architecture/00_整体架构规范.md)。

零依赖 Node 后端 + Next.js 前端双容器编排，一条命令起服务，数据自动持久化，崩溃自动重启。

**入口**：`http://<ip>:${WEB_PORT}`（Next.js 前端，`/api/*` 反代到后端容器；唯一 Web 入口——Phase 5 后旧静态前端已删除，3300 不再对外暴露）。端口由服务器 `.env` 的 `WEB_PORT` 决定（compose 默认 3000；当前线上同机 3000 已被其他服务占用，实际用 **3002**）。

## 二、前置条件

- **一台阿里云 ECS**：建议 2 核 2G 起（本服务极轻）；操作系统 CentOS/Ubuntu/Alibaba Cloud Linux 均可。
- **安装 Docker**（如未安装）：
  ```bash
  curl -fsSL https://get.docker.com | bash -s docker
  sudo systemctl enable --now docker
  ```

## 三、快速部署（推荐：ECS 上直接构建）

1. **上传包到 ECS**（任选）：
   - 控制台：把整个 `zhibi-vantage-docker` 目录压缩上传，`unzip` 解压；
   - 或本机执行：`scp -r zhibi-vantage-docker root@<ECS公网IP>:/opt/`

2. **进入目录并部署**：
   ```bash
   cd /opt/zhibi-vantage-docker
   cp .env.example .env     # 建议在 .env 里设置 MT_MASTER_KEY（见第五节）
   bash scripts/deploy.sh
   ```

3. **放行安全组端口**（必做，否则外网打不开）：
   - 阿里云控制台 → ECS → 安全组 → 配置规则 → 入方向：
     - 协议 TCP，端口 `3000`，源 `0.0.0.0/0`（或你的办公网 IP，更安全）

4. **访问**：浏览器打开 `http://<ECS公网IP>:${WEB_PORT:-3000}`

> 首次启动会自动把 `config-seed/config.json`（密钥位默认为空）写进数据卷，之后修改密钥请在页面"设置"里操作，容器重启不会覆盖。

## 四、备选：本机构建后导入（无网/慢网 ECS 场景）

1. 本机（已装 Docker）在包目录执行：
   ```bash
   docker compose build
   docker save zhibi-vantage:1.5.0 zhibi-web:0.2.0 | gzip > zhibi-vantage-images.tar.gz
   ```
2. 上传 tar 到 ECS，执行：
   ```bash
   docker load < zhibi-vantage-images.tar.gz
   cd /opt/zhibi-vantage-docker && bash scripts/deploy.sh
   ```
   （`deploy.sh` 里 `up -d --build` 会直接复用已加载的镜像。）

## 六、数据持久化与备份

- **数据都在 Docker 命名卷 `zhibi_data`**（映射容器内 `/app/data`）：档案、配置、数据库、日志。
- **容器删除/重建不丢数据**；只有显式 `docker volume rm zhibi_data` 才会清空。
- **定期备份**（建议每日，可加 crontab）：
  ```bash
  bash scripts/backup.sh          # 生成 backups/zhibi-data-<时间戳>.tar.gz
  ```
- 恢复：
  ```bash
  docker run --rm -v zhibi_data:/data -v $(pwd)/backups:/backup \
    alpine tar xzf /backup/zhibi-data-<时间戳>.tar.gz -C /data
  ```

## 八、常见问题（FAQ）

**Q1：外网打不开？**
先确认：① 安全组已放行 `WEB_PORT`（当前线上 3002）；② `curl http://127.0.0.1:${WEB_PORT:-3000}/login` 返回 200；③ `curl http://127.0.0.1:${WEB_PORT:-3000}/healthz` 返回 200（后端经代理）；④ ECS 用的是按量公网 IP/已绑定弹性 IP。

**Q2：容器起来了但 health 一直 starting/unhealthy？**
`bash scripts/logs.sh`（后端）或 `docker compose logs zhibi-web`（前端）看报错。后端常见：`MT_MASTER_KEY` 与已加密配置不匹配（改回原密钥或清空数据卷中的 config.json 重新播种）。前端常见：构建期网络问题导致 `pnpm install` 失败——重跑 `docker compose build zhibi-web`。

**Q3：换 API 密钥怎么改？**
页面「设置」里直接改（推荐）；或停止容器后编辑数据卷中的 `data/config.json` 再启动。

**Q4：怎么设域名 + HTTPS？**
ECS 装 Nginx 反代：`80/443 → 127.0.0.1:${WEB_PORT:-3000}`，用 certbot 签免费证书；安全组放行 80/443 即可，`WEB_PORT` 可仅对内。

## 十、部署健康门与缓存策略（deploy-cron v3）

### 10.1 稳定入口与蓝绿切换

`3002` 由宿主机 **nginx** 持有（`scripts/nginx/zhibi.conf`），不再由 docker 端口映射直接暴露。
前端以 `blue(3102)` / `green(3202)` 双槽交替：候选容器先克隆当前运行容器的 env/网络在候选槽启动，
自身 `/login` 与全部静态资源验证通过、后端联通验证通过后，nginx 写 upstream 文件并 `reload` 原子切换，
旧槽保留 **120 秒排空期**后才停止——部署期间入口不中断，用户不会拿到半套 HTML/JS。

后端（compose 单实例，含 scheduler 与数据卷）在**数秒维护窗口**内替换：`/etc/nginx/zhibi_maintenance`
存在时入口返回明确的 `503 + 维护页`（不是随机 502、不是连接拒绝）。同一时刻只有一个后端消费数据卷，
不存在两个 scheduler 并行。

一次性迁移：`bash scripts/migrate-to-blue-green.sh`（3002 由 docker-proxy 交接给 nginx + blue 槽）。

### 10.1b 静态资源跨 release 回退（旧页面不因发布而失效）

切换后新 release 里不存在旧页面引用的 chunk 文件名。nginx 对 `/_next/static/` 先问当前槽，
**404 时回退到 `zhibi_web_previous`（排空期内仍存活的上一槽）**；回退也失败则如实返回 404，
绝不返回 502。由此「已打开的旧页面 + 新发布」不会出现 chunk load error，内容哈希文件也能安全地长期缓存。

### 10.2 健康门（判定"部署成功"的唯一标准）

- **基线**：在候选前端与新后端**启动之后**取容器 ID 与 `RestartCount`（部署前的旧容器 ID 本就该变化，不能作基线）。
- **A 启动等待**：候选前端 `/login` 200 + 后端 `healthy`（各 ≤60s）。
- **B 连续验收**（100 轮 × 3s ≈ 5 分钟）：
  1. 每轮 `/healthz` 与 `/login` 必须 200，0 次 502、0 次连接失败；
  2. 每 5 轮解析 HTML 引用的全部 `/_next/static` 资源，校验 200 + Content-Type；
  3. 每 10 轮校验候选前端与新后端的容器 ID / RestartCount 与基线一致；
  4. 全部通过才更新 `deployed_sha`、输出 `deploy done`、推送飞书。

### 10.3 统一回滚（幂等，只执行一次）

从"首次改动运行服务"（启动候选前端）起，任何非零退出都由 `trap` 触发回滚；构建阶段失败不动运行服务、
不触发回滚。回滚动作：维护态 → nginx 切回旧槽 → 后端恢复锚点镜像 → 停候选容器 → 关维护态 →
五项验证（`/login`、`/healthz`、全部静态资源、前后端健康、**镜像 ID 与锚点严格一致**）。
回滚失败明确报警并保留现场，不打印"已恢复"。

### 10.4 部署状态（仓库外，原子写）

`/var/lib/zhibi-deploy/state.json`：`deployed_sha` / `deployed_web_image_id` / `deployed_api_image_id` /
`active_web_slot` / `failed_sha` / `deployed_at`。要点：

- cron 以 **remote main 与 `deployed_sha`** 比较决定是否部署，不再用工作树 HEAD 代替运行版本；
- 只有健康门全过才更新 `deployed_sha`；回滚后保持旧值；
- 同一 `failed_sha` 不会每分钟重复部署，只有出现新 SHA 或 `FORCE_DEPLOY=1` 才重试；
- 状态文件不含任何密钥或配置正文。

### 10.5 缓存策略（防"旧 HTML 引用已删除 chunk"）

- **HTML / App Router 页面 / API 代理响应**：`Cache-Control: no-store, max-age=0`（`web/src/middleware.ts`）。
  此前页面返回 `s-maxage=31536000`，浏览器缓存的旧 HTML 在每次部署（buildId 更名）后引用已删除的旧 chunk，
  产生随机 502 与 chunk load error。
- **`/_next/static/*`**（内容哈希）：`public, max-age=31536000, immutable`。
- 404 与错误页同样不长期缓存（middleware 对全部非静态响应生效）。
- 行为验证在真实 HTTP 响应上执行（`scripts/deploy-regression.sh` R7），不做源码字符串检查。

### 10.6 并发、回归与镜像保留

- 部署脚本内部持有 `/tmp/zhibi-deploy.inner.lock`（flock -n），任何来源的并发部署第二个实例立即退出；
  锁由进程退出自动释放，成功与失败路径一致。
- 部署级回归：`bash scripts/deploy-regression.sh [--skip-rebuild]`（锁互斥 / 构建期失败不回滚 /
  真实替换 / 成功全过程探测 / 失败回滚全过程探测 / failed_sha 隔离 / 缓存头 / 锁释放）。
- 镜像保留：`zhibi-web:deployed-<sha>`（当前运行）、`:rollback`（上一成功）、`:cand-<sha>`（候选）。
  自动清理见 10.12 历史版本保留策略；`zhibi_data` 数据卷永不清理。

### 10.7 提交态收敛与被打断部署的自愈（deploy-cron v4）

- **状态只在最后提交**：`deployed_sha`/镜像 ID/active slot 在健康门 100 轮 + 最终核验
  （入口三端点 200、静态 0 异常、双容器 healthy）全部通过后，才原子写入
  `/var/lib/zhibi-deploy/state.json`，并置 `COMMITTED=1`。此后仅剩旧槽排空/静态归档
  修剪/镜像清理等容错步骤——任何异常（含 SIGTERM）都不再回滚运行版本，
  杜绝"状态=新版、运行=旧版"的自相矛盾。
- **in-flight 登记**：首次改动运行服务前写入 `inflight.json`
  （目标 sha/web/api 镜像/目标槽位），提交成功即删除。
- **reconcile（四方一致性核对）**：脚本每次启动（含 cron 命中暂停标记时）先核对
  状态文件 vs nginx active upstream vs 实际容器 vs 镜像 ID：
  - 被打断的部署若已实际接管入口且候选/后端均 healthy → **滚动提交**（写状态，视为完成）；
  - 其余一切不一致 → 以状态文件为准恢复：回切 nginx、重建/重启状态槽容器、
    后端镜像回滚到状态锚点、清理候选与残留槽容器，最后做就绪核验。
  - 可单独运行：`bash scripts/deploy-cron.sh --reconcile`。
- **SIGTERM 语义**：`trap 'exit 143' TERM` 保证 EXIT trap 收敛——提交前中断走统一回滚，
  提交后中断只记录不回滚。三断点（切换后/健康门期间/提交后排空期）由回归 R9 确定性覆盖。

### 10.8 静态资源多版本归档（旧页面保护不再有 120s 时限）

- 每个候选/运行版本的 `/_next/static` 通过 `docker cp` 并入宿主机
  `/var/lib/zhibi-static/_next/static/`（内容哈希文件名跨 release 唯一，直接累积合并）。
- nginx `/_next/static/` 三层供给：磁盘归档 → active 槽代理 → 上一槽代理 → 404 兜底。
  旧页面在旧槽停止（排空窗结束后）任意时间引用的 chunk 都命中磁盘，保护无时限。
- 候选静态归档失败 = 硬失败（拒绝上线）；自举失败仅告警。超过 60 天的归档文件在部署尾修剪。
- 回归 R11 实证：旧槽已停止后，旧 release 独有 chunk 经入口仍 200。

### 10.9 构建资源隔离与镜像溯源（1.9GB 机器铁律）

- **禁止 `--no-cache` 全量重建**（两次压死实录：磁盘 100%、OOM）。cron 正式路径只做
  缓存串行构建（`docker compose build`，受 inner lock 串行 + 资源预检门槛约束）。
- **预构建镜像部署**（生产推荐）：`ZB_PREBUILT_WEB_IMG` / `ZB_PREBUILT_API_IMG`
  显式提供镜像，部署门校验镜像 label `zb.commit`/`zb.tree` 与目标提交/树一致，
  缺 label 或错位一律拒绝（fail-closed）。缓存构建路径在构建后同样自检 label。
- 镜像溯源三元组（commit / tree / image Id+RepoDigests）落盘
  `/var/lib/zhibi-deploy/release-<short>.json`，与状态文件、实际容器可交叉核对。

### 10.10 密钥临时文件零残留

- 候选容器 env 文件（`mktemp /tmp/zhibi-cand-env.*`）与部署日志一律登记进
  `registered-tmp.list`，由统一 EXIT trap 清理——候选启动失败、SIGTERM、回滚失败
  等所有路径都不残留。
- 回归 R10 用受控假密钥标记（`ZB_TEST_SECRET_MARKER`）做全路径残留扫描：
  部署成功、失败回滚、SIGTERM 三条路径跑完后，`/tmp` 全域与 `/var/lib/zhibi-deploy`
  必须零命中。状态文件/发布清单从不包含密钥或配置正文。

### 10.11 r4 收尾增补（提交窗口 / 硬中断 / 串行构建 / drill 门禁）

- **提交窗口消除**：release manifest 与 `deployed-<sha>` 标签在状态原子替换**之前**完成；
  `state_write` 是最后一个必要的可失败操作，其后立即置 `COMMITTED=1`。即便进程恰在
  两者之间被 SIGTERM 打断，`on_exit` 会读取持久状态（`deployed_sha==NEW` 且镜像一致且
  入口已切换）判定为已提交——不存在"状态新版、运行旧版"的窗口。
- **in-flight phase 语义**：`inflight.json` 记录 `candidate_started / switched /
  health_verified` 三阶段。reconcile **只允许在持久化 `phase=health_verified`** 且入口、
  静态、双容器、镜像复验全部通过时滚动提交；nginx 已切换但 phase 未达标（含 SIGKILL
  等 EXIT trap 完全失效的硬中断）一律按旧 state 恢复，不得凭 Docker healthy 直接提交。
  恢复路径带维护窗（明确 503）并清理硬中断遗留的登记临时文件。
- **串行缓存构建**：禁止裸 `docker compose build`（会并行构建全部服务）。后端
  （zhibi-vantage）→ 前端（zhibi-web）按明确顺序分别构建，客户端 `nice -n 19` +
  `ionice -c3`（可用时）降级。回归用 docker shim 记录调用时间戳，行为级证明两服务
  无并行。构建窗口全程被现网探测覆盖；若现网/第三方测点出现服务超时，本机构建必须
  退回"仅预构建镜像"路径——**预构建镜像部署仍是推荐的正式路径**。
- **drill 门禁**：`ZB_SKIP_BUILD` 仅允许显式 `ZB_DRILL_MODE=1` 的回归演练使用；
  cron/main 部署或缺标记一律拒绝。drill 不打 `deployed-<sha>` 标签、不写 release
  manifest——历史镜像不得被正式登记为目标 commit/tree 的已部署产物；回归结束时按
  部署前快照恢复正式 state 并 reconcile 复核。

### 10.12 历史版本保留策略（2026-10-30，防无界增长）

每次部署会产生新的历史痕迹：`cand-<sha>`/`deployed-<sha>` 两组镜像标签、一份
release manifest、一批构建缓存。此前尾部只清 48h 前的悬空镜像层，带标签的历史版本与
构建缓存无限累积（审计实测：40G 盘悬空镜像 1.2GB、构建缓存 3.7GB 可回收、manifest
逐份增长）。现部署成功尾部统一执行 `history_prune`：

- **镜像标签**：`cand-*`/`deployed-*` 只保留最近 5 个 release + state.json 当前锚点 +
  本次候选；`:rollback` 与版本号标签（`1.5.0`/`0.2.0`）永不删除；
- **悬空镜像层**：删标签后立即 `docker image prune -f` 回收（不再等 48h）；
- **构建缓存**：`docker builder prune --keep-storage 3gb` 封顶，超出按 LRU 回收，
  增量构建速度不受影响；
- **release manifest**：`/var/lib/zhibi-deploy/release-*.json` 保留最近 20 份；
- 只操作 `zhibi-vantage`/`zhibi-web` 两个镜像仓库的 `cand-*`/`deployed-*` 标签，
  同机其他项目镜像不受影响；被容器引用的镜像删除自然失败并跳过。

配套修复（同一问题族）：

- **cron 快照引导** `scripts/deploy-boot.sh`：cron 不再调用仓库外的旧版脚本副本
  （此前 cron 跑的 `/opt/zhibi-vantage/deploy.sh` 与仓库版本脱节且无法自动更新），
  改为复制 `scripts/deploy-cron.sh` 到临时文件后运行——部署中 `git reset --hard`
  不会原地覆盖运行中的脚本，仓库脚本由此成为唯一源，git 拉取后下一分钟自动生效；
- **部署日志轮转** `scripts/logrotate-zhibi-deploy.conf` → `/etc/logrotate.d/zhibi-deploy`：
  cron 每分钟追加例行结果（暂停/无需部署各占一行，约 1400 行/天），weekly +
  maxsize 50M 轮转、保留 8 份压缩；
- **容器 stdout 日志封顶**：`docker-compose.yml` 两个 zhibi 服务加
  `logging: json-file, max-size 50m, max-file 3`（json-file 默认无上限）；
- **备份保留**：`scripts/backup.sh` 只保留最近 14 份备份（数据卷数百 MB/份，
  若按文档建议加入每日 crontab，无上限会持续吃盘）。
