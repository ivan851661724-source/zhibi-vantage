# 知彼 Vantage 部署与运行

状态：运行操作说明。命令均在仓库根目录执行。当前服务、构建路径、端口和镜像版本以[编排文件](../../docker-compose.yml)、[后端镜像](../../Dockerfile)及[前端镜像](../../web/Dockerfile)为准；本文不自动授权部署或发送通知。整体结构见[整体架构规范](../architecture/00_整体架构规范.md)。

零依赖 Node 后端 + Next.js 前端双容器编排，一条命令起服务，数据自动持久化，崩溃自动重启。

**入口**：`http://<ip>:${WEB_PORT}`（Next.js 前端，`/api/*` 反代到后端容器；唯一 Web 入口——Phase 5 后旧静态前端已删除，3300 不再对外暴露）。端口由服务器 `.env` 的 `WEB_PORT` 决定（compose 默认 3000；当前线上同机 3000 已被其他服务占用，实际用 **3002**）。

## 二、前置条件

- **一台阿里云 ECS**：建议 2 核 2G 起（本服务极轻）；操作系统 CentOS/Ubuntu/Alibaba Cloud Linux 均可。
- **安装 Docker**（如未安装）：
  ```bash
  curl -fsSL https://get.docker.com | bash -s docker
  sudo systemctl enable --now docker
  ```

## 三、快速部署（推荐：ECS 上直接构建）

1. **上传包到 ECS**（任选）：
   - 控制台：把整个 `zhibi-vantage-docker` 目录压缩上传，`unzip` 解压；
   - 或本机执行：`scp -r zhibi-vantage-docker root@<ECS公网IP>:/opt/`

2. **进入目录并部署**：
   ```bash
   cd /opt/zhibi-vantage-docker
   cp .env.example .env     # 建议在 .env 里设置 MT_MASTER_KEY（见第五节）
   bash scripts/deploy.sh
   ```

3. **放行安全组端口**（必做，否则外网打不开）：
   - 阿里云控制台 → ECS → 安全组 → 配置规则 → 入方向：
     - 协议 TCP，端口 `3000`，源 `0.0.0.0/0`（或你的办公网 IP，更安全）

4. **访问**：浏览器打开 `http://<ECS公网IP>:${WEB_PORT:-3000}`

> 首次启动会自动把 `config-seed/config.json`（密钥位默认为空）写进数据卷，之后修改密钥请在页面"设置"里操作，容器重启不会覆盖。

## 四、备选：本机构建后导入（无网/慢网 ECS 场景）

1. 本机（已装 Docker）在包目录执行：
   ```bash
   docker compose build
   docker save zhibi-vantage:1.5.0 zhibi-web:0.2.0 | gzip > zhibi-vantage-images.tar.gz
   ```
2. 上传 tar 到 ECS，执行：
   ```bash
   docker load < zhibi-vantage-images.tar.gz
   cd /opt/zhibi-vantage-docker && bash scripts/deploy.sh
   ```
   （`deploy.sh` 里 `up -d --build` 会直接复用已加载的镜像。）

## 五、环境变量说明（`.env`）

| 变量 | 默认 | 说明 |
|---|---|---|
| `MT_MASTER_KEY` | 空 | **强烈建议设置**。设置后 API 密钥以加密形式落盘。生成：`openssl rand -hex 32`。⚠️ 一旦使用，请妥善保存——丢失将无法解密已加密的密钥 |
| `PORT` | 3300 | 服务端口（一般不用改） |
| `SCHEDULER_ENABLED` | 1 | 每日定时雷达扫描（0 关闭） |
| `ZB_QUOTA_ENABLED` | 0 | 配额硬拦截（默认仅展示不拦截） |

## 六、数据持久化与备份

- **数据都在 Docker 命名卷 `zhibi_data`**（映射容器内 `/app/data`）：档案、配置、数据库、日志。
- **容器删除/重建不丢数据**；只有显式 `docker volume rm zhibi_data` 才会清空。
- **定期备份**（建议每日，可加 crontab）：
  ```bash
  bash scripts/backup.sh          # 生成 backups/zhibi-data-<时间戳>.tar.gz
  ```
- 恢复：
  ```bash
  docker run --rm -v zhibi_data:/data -v $(pwd)/backups:/backup \
    alpine tar xzf /backup/zhibi-data-<时间戳>.tar.gz -C /data
  ```

## 八、常见问题（FAQ）

**Q1：外网打不开？**
先确认：① 安全组已放行 `WEB_PORT`（当前线上 3002）；② `curl http://127.0.0.1:${WEB_PORT:-3000}/login` 返回 200；③ `curl http://127.0.0.1:${WEB_PORT:-3000}/healthz` 返回 200（后端经代理）；④ ECS 用的是按量公网 IP/已绑定弹性 IP。

**Q2：容器起来了但 health 一直 starting/unhealthy？**
`bash scripts/logs.sh`（后端）或 `docker compose logs zhibi-web`（前端）看报错。后端常见：`MT_MASTER_KEY` 与已加密配置不匹配（改回原密钥或清空数据卷中的 config.json 重新播种）。前端常见：构建期网络问题导致 `pnpm install` 失败——重跑 `docker compose build zhibi-web`。

**Q3：换 API 密钥怎么改？**
页面「设置」里直接改（推荐）；或停止容器后编辑数据卷中的 `data/config.json` 再启动。

**Q4：怎么设域名 + HTTPS？**
ECS 装 Nginx 反代：`80/443 → 127.0.0.1:${WEB_PORT:-3000}`，用 certbot 签免费证书；安全组放行 80/443 即可，`WEB_PORT` 可仅对内。

## 九、安全提醒

- `config-seed/config.json` 默认不包含真实 API Key。真实密钥应通过部署环境变量或设置页安全配置，严禁提交到 Git 仓库。
- 生产环境建议：设 `MT_MASTER_KEY` 加密密钥、安全组限制来源 IP、定期备份 `zhibi_data`。
- 镜像以非 root 用户（`node`）运行，唯一对外端口为 `WEB_PORT`（当前线上 3002；后端 3300 仅容器网络内可达）。

## 十、部署健康门与缓存策略（deploy-cron v3）

### 10.1 稳定入口与蓝绿切换

`3002` 由宿主机 **nginx** 持有（`scripts/nginx/zhibi.conf`），不再由 docker 端口映射直接暴露。
前端以 `blue(3102)` / `green(3202)` 双槽交替：候选容器先克隆当前运行容器的 env/网络在候选槽启动，
自身 `/login` 与全部静态资源验证通过、后端联通验证通过后，nginx 写 upstream 文件并 `reload` 原子切换，
旧槽保留 **120 秒排空期**后才停止——部署期间入口不中断，用户不会拿到半套 HTML/JS。

后端（compose 单实例，含 scheduler 与数据卷）在**数秒维护窗口**内替换：`/etc/nginx/zhibi_maintenance`
存在时入口返回明确的 `503 + 维护页`（不是随机 502、不是连接拒绝）。同一时刻只有一个后端消费数据卷，
不存在两个 scheduler 并行。

一次性迁移：`bash scripts/migrate-to-blue-green.sh`（3002 由 docker-proxy 交接给 nginx + blue 槽）。

### 10.2 健康门（判定"部署成功"的唯一标准）

- **基线**：在候选前端与新后端**启动之后**取容器 ID 与 `RestartCount`（部署前的旧容器 ID 本就该变化，不能作基线）。
- **A 启动等待**：候选前端 `/login` 200 + 后端 `healthy`（各 ≤60s）。
- **B 连续验收**（100 轮 × 3s ≈ 5 分钟）：
  1. 每轮 `/healthz` 与 `/login` 必须 200，0 次 502、0 次连接失败；
  2. 每 5 轮解析 HTML 引用的全部 `/_next/static` 资源，校验 200 + Content-Type；
  3. 每 10 轮校验候选前端与新后端的容器 ID / RestartCount 与基线一致；
  4. 全部通过才更新 `deployed_sha`、输出 `deploy done`、推送飞书。

### 10.3 统一回滚（幂等，只执行一次）

从"首次改动运行服务"（启动候选前端）起，任何非零退出都由 `trap` 触发回滚；构建阶段失败不动运行服务、
不触发回滚。回滚动作：维护态 → nginx 切回旧槽 → 后端恢复锚点镜像 → 停候选容器 → 关维护态 →
五项验证（`/login`、`/healthz`、全部静态资源、前后端健康、**镜像 ID 与锚点严格一致**）。
回滚失败明确报警并保留现场，不打印"已恢复"。

### 10.4 部署状态（仓库外，原子写）

`/var/lib/zhibi-deploy/state.json`：`deployed_sha` / `deployed_web_image_id` / `deployed_api_image_id` /
`active_web_slot` / `failed_sha` / `deployed_at`。要点：

- cron 以 **remote main 与 `deployed_sha`** 比较决定是否部署，不再用工作树 HEAD 代替运行版本；
- 只有健康门全过才更新 `deployed_sha`；回滚后保持旧值；
- 同一 `failed_sha` 不会每分钟重复部署，只有出现新 SHA 或 `FORCE_DEPLOY=1` 才重试；
- 状态文件不含任何密钥或配置正文。

### 10.5 缓存策略（防"旧 HTML 引用已删除 chunk"）

- **HTML / App Router 页面 / API 代理响应**：`Cache-Control: no-store, max-age=0`（`web/src/middleware.ts`）。
  此前页面返回 `s-maxage=31536000`，浏览器缓存的旧 HTML 在每次部署（buildId 更名）后引用已删除的旧 chunk，
  产生随机 502 与 chunk load error。
- **`/_next/static/*`**（内容哈希）：`public, max-age=31536000, immutable`。
- 404 与错误页同样不长期缓存（middleware 对全部非静态响应生效）。
- 行为验证在真实 HTTP 响应上执行（`scripts/deploy-regression.sh` R7），不做源码字符串检查。

### 10.6 并发、回归与镜像保留

- 部署脚本内部持有 `/tmp/zhibi-deploy.inner.lock`（flock -n），任何来源的并发部署第二个实例立即退出；
  锁由进程退出自动释放，成功与失败路径一致。
- 部署级回归：`bash scripts/deploy-regression.sh [--skip-rebuild]`（锁互斥 / 构建期失败不回滚 /
  真实替换 / 成功全过程探测 / 失败回滚全过程探测 / failed_sha 隔离 / 缓存头 / 锁释放）。
- 镜像保留：`zhibi-web:deployed-<sha>`（当前运行）、`:rollback`（上一成功）、`:cand-<sha>`（候选）。
  自动清理只删 48h 前的 dangling，带上述 tag 的镜像不受影响；`zhibi_data` 数据卷永不清理。
