# SC-04 · 核心竞争情报主闭环（竞品数据库 → 情报库 → 机会视图 → 调研报告）

**状态**：已实现（随 `review/core-product-framework` 分支，未合并 main）
**日期**：2026-10-18
**上位依赖**：00 v1.2（工程基线）、01 v1.5.0（产品宪法）、02–07 v0.4（SC-03 修订）、SC-01（快照真值链）、SC-02（Data Surface 采集基础设施）、SC-03（Competitive Data Network）
**服从关系**：与 SC-03 冲突处以 SC-03 与 v1.5 宪法为准；本变更不把任何未接入 provider 标记为已实现。

---

## 1. 目标与边界

- 建立用户真正使用的主闭环：**竞品数据库 → 情报库 → 机会视图 → 调研报告**。
- Data Surface 降级为**底层数据入口**，在品牌详情页以「数据覆盖与来源」呈现，不作为独立开发者面板。
- 本批**不接入任何新外部 provider**：当前只有 Shopify 公开商品目录具备真实接入能力；广告、社媒、KOL、评论、搜索热度、流量、经营估算一律显示「未接入 / 覆盖不足 / 暂无可靠数据」，**不得用 mock、LLM 推测或空壳数字填充**。
- 严格遵循 v1.5 宪法：不要求连接订单/ERP/CRM/广告/支付/客户数据；不代替商家做经营决策；不把推断包装成事实；每个用户可见结论带数据性质、时间、覆盖范围与证据入口；数据不足时明确说明不能回答什么。

## 2. 真值链与读模型边界

- 原始真值链不变：`SourceSnapshot → Evidence → Fact → Metric → DomainEvent → Judgment`。
- 新增读模型**只做投影与索引，不复制、不篡改原始真值**：
  - Brand Record：Workspace 内稳定品牌档案；
  - Brand ↔ Project Link：品牌在项目/市场/品类/竞争关系中的适用范围；
  - Brand Source Identity：官网、Shopify 身份链接（沿用 Data Surface，未核实保持 unresolved）；
  - Brand Timeline Index：价格、商品、监控事件、资料缺口、纠错、报告生成的时间线索引；
  - Research Report 与 Report Citation：报告版本、生成范围、冻结事实包、引用 Evidence/Snapshot、覆盖缺口、生成时间。
- 第一版只做 **Workspace 内 Canonical Brand**，不跨租户、跨 Workspace 合并公共品牌事实。

## 3. 数据表（brands.db，独立库，不触碰既有库）

| 表 | 用途 | 关键约束 |
|---|---|---|
| `brand_records` | 品牌档案 | 租户硬隔离；按 域名 / competitor_ref 幂等 |
| `brand_project_links` | 品牌↔项目适用范围 | UNIQUE(tenant, brand, project) |
| `brand_timeline` | 时间线索引 | (tenant, brand, kind, at, ref_id) 幂等，重放不重复 |
| `reports` | 报告版本与冻结事实包 | 租户 + 项目 |
| `report_citations` | 报告事实引用 | 租户 + 报告 |
| `report_jobs` | 报告生成持久任务 | claimToken 租约 / retry / reclaim |

## 4. 情报项

- 字段：品牌、时间、类型（价格/商品/促销/渠道/口碑/资料缺口/监控状态）、数据性质、当前状态、证据入口、用户纠错入口。
- **数据性质（用户语言）**：来源直接记录 / 官方公开数据 / 数据服务估算 / 按已有数据计算 / 根据公开内容归纳。
- **状态**：已核实 / 待核实 / 资料不足 / 来源冲突。
- 规则：**没有 Evidence 的内容不得标记「已核实」**；没有充分数据的推断不得伪装成事件事实。

## 5. 机会视图

- 接统一读模型（不再只依赖旧版临时竞品状态）：先展示「已具备什么数据」（品牌数、已具备真实数据的品牌数、维度覆盖），再展示机会。
- 每条机会标注：事实依据、时间范围、覆盖品牌数、限制，并声明「机会只是待验证线索，不是经营建议或确定结论」。
- **样本不足（< 3 个已具备真实数据覆盖的品牌）→ 明确「资料不足，暂不生成机会判断」**，不输出机会结论。
- 未接入维度（广告/社媒/评论/搜索/流量/经营估算）只出现在「限制」清单，绝不作为机会依据。

## 6. 报告与引用冻结

- 生成**只由用户显式触发**（`POST /api/reports`），页面加载不消耗模型额度。
- 使用**生成时刻冻结的事实包**（facts / coverage / gaps / opportunities），实时数据变化不改写已生成报告。
- LLM 只组织已批准事实（沿用 `research/report.js` 的强制引用与校验器）；**LLM 不可用时返回带事实清单、引用与资料缺口的结构化报告，不伪造完整分析**。
- 任务持久化：`report_jobs`（queued/running/success/failed，租约 + 心跳 + reclaim + retry 3 次），重启后可恢复或明确失败（retry 耗尽 → dead + report failed，绝不永久 running）。
- 支持查看、重新生成、下载 Markdown；PDF 导出列为后续项。

## 7. API（tenant-scoped，跨租户统一 404）

| Method | Path | 说明 |
|---|---|---|
| GET | `/api/brands?projectId=` | 竞品库列表（覆盖/最近观察/最近变化/缺口） |
| GET | `/api/brands/:brandId` | 品牌详情（概览/商品与价格/时间线/覆盖/情报/报告） |
| GET | `/api/brands/:brandId/timeline` | 品牌时间线（kind/nature/from/to/limit） |
| GET | `/api/brands/:brandId/coverage` | 数据覆盖与来源 |
| GET | `/api/intelligence?projectId=&brandId=&type=&from=&to=` | 情报库（可筛选） |
| GET | `/api/opportunities?projectId=` | 机会视图（含样本范围与限制） |
| GET | `/api/reports?projectId=` | 报告列表 |
| POST | `/api/reports` | 生成报告（202 + 持久任务） |
| GET | `/api/reports/:reportId` | 报告详情（正文/引用/覆盖/缺口/任务） |

所有读取校验项目、品牌、报告与 Evidence 属于当前租户；跨租户 404，不泄露存在性。

## 8. 页面

- 竞品库 `/brands`：品牌名、官网或已核实身份、市场/品类/竞争关系、覆盖状态、最近观察时间、最近重要变化、未接入或资料缺口。
- 品牌详情 `/brands/:brandId`：概览、商品与价格、竞争动态时间线、数据覆盖与来源（Data Surface 区域）、情报、相关报告。已有 `IntelProfile` 的旧能力接入统一读模型，不保留两套彼此无关的数据展示。
- 情报库 `/intel`（扩展）：按品牌/类型/时间筛选，证据入口，纠错入口。
- 机会视图 `/opportunity`（扩展）：数据基础与样本范围 + 机会线索与限制。
- 调研报告 `/report` + `/report/:reportId`：列表、生成、正文、生成范围、数据覆盖、事实引用、机会与限制、版本与生成时间、纠错入口、Markdown 下载。

## 9. 统一证据与历史表达

- 每条来源显示：来源名称、初始 URL 与最终 URL、观察时间、数据性质、SourceSnapshot / Evidence 标识、内容哈希或可核验标识、来源状态。
- **不得展示**服务器文件路径、内部错误码、调用栈、密钥、原始 payload 路径。
- 时间线区分：Vantage 当时观察到 / 后续补入的历史 / 按已有数据计算 / 根据公开内容归纳 / 用户纠错与更正。
- 无网页存档或数据商历史接入时**只展示「开始观察日期」**，不暗示拥有更早历史。

## 11. 验收场景

1. 新用户创建项目、添加竞品后可进入竞品库。
2. 未采集竞品显示「尚未采集」，不显示「未发现数据」。
3. Shopify 竞品刷新后，商品、价格、快照、证据、时间线、情报库与报告引用贯通。
4. 未接入维度（广告/社媒/评论/搜索/流量/经营估算）显示缺口，不产生伪数据。
5. 情报库可按品牌、类型、时间筛选，并能打开正确证据。
6. 机会视图样本不足时不输出机会结论；满足时显示依据与限制。
7. 报告事实、机会、缺口与引用可追溯；实时数据变化不改写已生成报告。
8. 两个租户不能读取彼此品牌、情报、报告、证据、快照或时间线。
9. robots 路径 P0 SSRF 回归通过（随本分支第一项带入）。
10. 后端完整测试零失败、前端构建通过、secret scan 通过、`git diff --check` 通过、全新数据目录启动与重启通过。

## 12. 与 SC-03 的关系

- SC-03 定义「要有哪些竞争数据能力、如何验收 GA」；SC-04 定义「已接入能力如何组织成用户可用的主闭环」。
- 本分支只完成**已批准的采集基础设施 + 读模型骨架**，不宣称 SC-03 中未接入 provider 已具备真实覆盖能力。
- 后续接入新 provider 时：先在 Registry 登记能力并通过 SC-03 的 POC/GA 验收，再由本读模型消费（维度状态自动从「未接入」转为真实状态）。
