# 搜索算法分析报告（v2 修订版）：为什么慢、为什么不准

> 日期：2026-10-02 ｜ v1 同日初稿，v2 按独立复核意见修订
> **代码基线**：本地 checkout `c17688c`（main）；复核基线上游 `456472c`（2026-09-15）。两版核心文件（llm-gateway / search / enrich / candidates / evidence / voice-collector / metrics / source-identity）已逐条比对，本报告引用行号均为本地版本。
> **证据等级标注**：〔代码〕= 直接读码确认；〔复现〕= 隔离复现证实（8 项，基于原函数拷贝，非全仓回归、非生产实测，脚本 minimal-repros.cjs）；〔估算〕= 条件估算，未经实测；〔待核实〕= 依赖生产环境，本地无法验证。
> **声明**：本轮未调用真实付费搜索/LLM 接口，所有耗时数字为结构推算，不冒充线上性能测试。

## 一、当前搜索算法概述

```
POST /api/discover（立即 202，SSE 推进度）
└─ runDiscover（app/research/discover.js:141）—「前台发现」
   ① 翻译 ∥ LLM 枚举，但 await Promise.all 两者的完成                        discover.js:187
   ② SERP 扇出第一轮 8-9 条（只依赖翻译结果，却等枚举结束才开始）              discover.js:199
   ③ harvest（LLM 从 snippet 提取候选）                                     discover.js:207
   ④ 扇出第二轮（≤3 补充 + ≤8 候选验证）                                    discover.js:214-224
   ⑤ 合并三路候选 → crossValidate → LLM 相关性裁判 → relevant && fit≥60 门槛  discover.js:243-247
   ⑥ presenceGate / rank / 域名去重                                        discover.js:248+
   ⑦ 逐竞品入队 → 后台深研
└─ runQueue（app/research/enrich.js:74）—「后台深研」
   while(true) 逐个 await deepResearchOne（enrich.js:99；按 projectId 隔离，单项目内串行）
   每竞品：锚点搜索 → 抓官网∥Shopify → 9 路探测（内部并发 3）→ 1 次全字段 LLM 抽取 → 口碑采集
```

字段产出的真实分工（v1 表述"字段值完全由 LLM 产生"已修正）：
- **代码裁决**：渠道存在性正负证据（`enrich.js:289-312`）、Shopify 结构化价格（`enrich.js:185-197`）、币种页面检测、官网正文价格规则提取、价格裁决树（`lib/pricefield.js`）。
- **LLM 产出**：翻译、枚举、harvest、相关性裁判、**多项语义字段（卖点/定位/口碑主题/成立年份/增长态势等）的全字段抽取**（`enrich.js:331-377`）。
- **置信度**：全部代码推导（`research/evidence.js:26-34` 等），LLM 无权自评——但推导只看"引用了哪些证据"，不看"证据是否支持该值"（见 A1，核心缺陷）。

关键配置（〔待核实〕项为本地 checkout 观察，不代表生产）：搜索仅 Serper 单源〔待核实生产 key 数〕；LLM 走阿里云百炼端点 deepseek-v4-flash〔待核实生产模型〕；`modelDeep` 未配置；搜索缓存 24h/7d、网页 72h，**LLM 零缓存**〔代码〕；`discover-stage`/`search-call`/`llm-call`/`llm-body` 埋点代码齐全，但本地日志零落盘，生产是否落盘〔待核实〕。

## 二、已确认的问题

### 慢（按确认置信度排序）

**S1〔代码〕单项目内，竞品深研串行。**
`runQueue` 循环内逐个 `await deepResearchOne`（`enrich.js:99`），任务间 sleep(150ms)。`CONCURRENCY=3` 只作用于单竞品内部探测（`enrich.js:39`）。队列按 `projectId` 隔离——**是"单项目内串行"，不是全服务零并行**。单竞品深研含 ~10-12 次搜索 + 1 次大 LLM + 抓页 + 采集，结构推算 60-120s〔估算〕；8-18 个竞品的项目后台收尾为 8-36 分钟量级〔估算，v1 的"8-25 分钟"收敛为此区间〕。**它是否为生产耗时的最大头，需阶段计时数据证实**，当前只能确认排队累积机制存在。

**S2〔代码〕前台关键路径有一个可以直接拆掉的多余等待。**
翻译和枚举已经并行，但 `await Promise.all([translateP, enumP])`（`discover.js:187`）让第一轮扇出（`discover.js:196-199`，其查询**只依赖翻译结果**）被枚举挡住。`llmCands` 迟到第二轮验证才需要（`discover.js:215-218`）。优化方向不是"合并翻译和枚举两个调用"（它们本来就并行，合并反而可能让慢响应挡住快响应），而是**扇出 1 只等翻译、与枚举重叠执行，到第二轮前再汇合**。

**S3〔代码+复现〕LLM 超时不覆盖响应正文读取 —— 比"漏配 90s"更根本。**
`rawCall` 的计时器在 `fetch()` 返回（响应头到达）后即被 `finally { clearTimeout }` 清除（`llm-gateway.js:55-66`），后续 `await r.json()` 在 `call()` 里执行、无任何 deadline（`llm-gateway.js:127`）。隔离复现：配置 60ms 超时，6ms 收到响应头，256ms 正文读完，**未被超时中断**。即所谓"45s 有界返回"只对响应头成立。注释里的 `llm-body` 埋点（`llm-gateway.js:129`）说明开发者已知"headers 快但 body 挂起"现象，但 deadline 本身没修。**任何超时预算调整都必须先让同一 deadline 覆盖请求→响应头→正文，否则上限计算不成立。**

**S4〔代码〕深研全字段抽取调用漏配超时参数（重新定性，v1 结论部分作废）。**
`enrich.js:377` 未传 `timeoutMs/maxAttempts`，走默认 45s×3。但按网关现行退避规则，45×3+1+2=**138s** 与 90×2+1=**181s**——改成 90×2 的**名义失败等待预算更长**，v1"消除每竞品最坏 +90s"的说法错误。它的真实价值是：对正常耗时落在 45-90s 的大输出任务，减少"被 45s 阈值中断→整轮重试→重复计费"〔估算，需供应商用量记录佐证计费影响〕。`discover.js:107` 注释记载的"45s 触发重试翻倍"历史事故支持这一动机。**实施顺序：先修 S3，再调此参数，并用成功耗时分布验证。**

**S5〔代码+复现〕口碑管线不只是串行，还存在两处"拿了平台却拿不到数据"的接线断裂。**
- 深研调用 `collectBrandVoice` 时未传 `config`（`enrich.js:592-596` 只传 maxItems/since/adapterOpts），而采集器内部 `const config = opts.config || {}`（`voice-collector.js:396`）——**该链路上 Trustpilot/Etsy/YouTube 等密钥型适配器一律按未配置处理。注册 5 个平台 ≠ 本轮真的请求了 5 个平台。**
- 独立站评论适配器给条目设 `date: null`（`voice-collector.js:357`），而归一化 `coerceVoiceItem` 对无有效时间的条目直接拒绝〔复现〕——该分支抽到的文本变不成有效口碑条目。
- 超时收窄：`_getJson` 无应用级超时属实（`voice-collector.js:104-111`），但独立站评论抓取已有每路径 10s 超时——"完全无超时"仅适用于 `_getJson` 路径。5 平台 for 循环串行（`voice-collector.js:402-416`）属实。
**优先顺序：先验证各适配器实际启用、产出有效数据，再谈并行化收益。**

**S6〔代码〕其余放大项（次要）**：LLM 零缓存（同赛道重跑 4 次 LLM 全量重算）；`saveState` 同步整卡读写（`core/state-store.js`）与 serper-budget 同步文件 RMW 在并发 discover 时阻塞事件循环；搜索层 failover 的耗时取决于错误类型（Serper 的 invalid/exhausted 换 key，网络/解析错误直接抛出进入下一 provider 或外层重试），**不能统一按 provider×key 乘积计算**（v1 该估算方式作废）。

### 不准（按确认置信度排序）

**A1〔代码+复现〕引用支持性校验缺失 —— 准确性核心风险。**
Prompt 要求"关键字段不允许留空：无证据也要推算"（`enrich.js:336`）；`citedEvs()` 只按编号反查证据对象存在（`enrich.js:380`）；`deriveBasis()` 见到任意 tier1 引用即返回 verified/high（`evidence.js:28-29`）。隔离复现：仅含欢迎语的 tier1 证据使 `deriveBasis` 返回 `{basis:'verified', confidence:'high'}`。**该规则没有能力区分"引用真实存在"与"引用真正支持结论"**——这不是证明某次生产输出造假，而是证明升级通道洞开。附带口径问题：无引用时 `applyBasis` 覆盖为 `inferred/low`（`enrich.js:386`），而 `deriveBasis([])` 本意是 `unverified/low`——纯猜测被计入"推测"桶而非"未探测"。

**A2〔代码+复现〕配额耗尽/探测失败会被深研层转成 verified 级"确认缺席"。**
`searchProvider` 在租户配额不足时返回 `{results:[], error:'quota', note:'SEARCH_QUOTA'}`（`search.js:67`）；发现层 `fanoutSearch` 会识别并上浮（`search.js:176-188`），但深研探测只取 `(await searchProvider(...)).results || []`（`enrich.js:224`）——**哨兵被丢弃，配额耗尽看起来像"搜索成功零命中"**。负证据分支条件是 `kept[chKey] != null && officialPage.ok`（`enrich.js:306`），复现证实 quota 空数组可通过。且该条件并非"搜索成功+零命中"的严格语义：**搜索有结果、只是没通过官方店铺规则时，同样落进"确认缺席"**。必须修的契约是：

> 配额不足 / 探测失败 / 检出但无官方店 / 确认不存在 —— 必须是四个不同状态；默认保留"未检出"，只有明确的、限定范围的否定证据才允许"确认缺席"。

v1"中文探测词 + gl=us → 恒零命中"降级为诱因举例：查询语言与市场不匹配**增加**零命中概率，但"恒零命中"不是代码能证明的事实（官网含 store locator 时线下渠道仍会被正证据确认）。真正的问题始终是**把未检出升级为确认缺席**，语言不匹配只是让它更容易发生。

**A3〔代码+复现〕准确率度量从冷启动就是坏的，删掉假金标也不会自动变好。**
自动金标把证据标题同时写进 `algoValue` 和 `humanValue` 并置 `correct:true, judge:'seed-auto'`（`metrics.js:425,475`）——用"存在 tier1 来源"冒充"抽取正确"。但门禁条件是 `a && a.accuracy != null && a.accuracy < redline`（`metrics.js:402`）：**无样本时条件不成立、照常放行**。只删 seed-auto 得到的是"没有数据"，不是"有效门禁"。需要同时引入"样本不足/未评估"状态，并规定高可信结论必须经过足量独立核验才可展示；用户主动纠错是有价值的反馈，但与随机抽检不是同一种采样，不宜直接当无偏准确率。

**A4〔代码〕"独立来源印证"可被转载刷高；防同稿机制没有接到实际裁决路径上。**
`deriveBasis` 按域名集合数独立 tier2（`evidence.js:30-31`）；SimHash 指纹去重已实现（`lib/source-identity.js:67-95,127-166`），但 `matchByFingerprint` 开关在全仓无调用点传入——**且即便打开别的模块的开关，`deriveBasis` 仍直接算域名集合，不会自动生效**（v1"启用开关即可"的暗示作废，需要把指纹比对接进 deriveBasis/adjudicate 的证据路径）。

**A5〔代码+复现〕实体身份、来源身份、域名解析三层混用。**
v1 两处判断已修正：① `mergeCandidates` 先按归一化名合并，同名候选有无 URL 会在合并阶段归一（复现证实），"有 URL 与无 URL 永不去重"不成立；② `_domains` 恒初始化（`candidates.js:165`，无 URL 时为空集），首项无 URL 不造成歧义漏检（复现：首项无 URL、后两项域名冲突 → 正常标 `entityAmbiguous`）。
仍然成立的风险：候选去重 key 双轨（`discover.js:318-319` 域名 key vs 名字 key）主要在**别名、不同写法、同名异实体**场景漏合；`net.domainOf` 不折叠子域与 `SI.extractDomain` 折叠并存；**`SI.extractDomain` 不能盲用作竞品身份键**——复现证实 `shop-a.myshopify.com` 与 `shop-b.myshopify.com` 都归一成 `myshopify.com`，直接替换会合并不同商家。三层身份（竞品实体 / 证据来源 / 域名解析）应分离，可共享底层解析但不得共享最终身份键。

**A6〔代码〕信源分级的真实缺口是 tier1，不是 tier2 白名单（v1 归因修正）。**
未列名域名（包括中文媒体）默认已返回 tier2（`evidence.js:23`，`return 2` 与白名单命中同值，复现证实）——**把中文媒体加进 TIER2 列表通常不改变任何分级**。真实缺口：TIER1 正则只覆盖 etsy/amazon stores/tiktok/instagram/youtube/facebook（`evidence.js:13`），**小红书/天猫/京东/淘宝的店铺页永远拿不到 tier1**，尽管系统专门为它们建了探测查询（`enrich.js:205-208`）和渠道链接正则。对中文渠道品牌，其渠道证据最多到 inferred，无法 verified。要补的是 **tier1 识别规则**，不是 tier2 名单。

**A7〔代码〕发现层过滤比 v1 描述的严格，但依据仍单薄。**
修正：存在 `relevant && categoryFit >= 60` 硬门槛（`discover.js:247`），裁判漏答的候选回落 harvest 自报分后仍须过 60 分，**并非无条件放行**。仍然成立的薄弱点：裁判每候选只喂 1 条 140 字 snippet（`candidates.js:270-273`）；matchScore 是 LLM 自报分且 `>=40` 硬门槛、60 分门槛的回落值都基于它；crossValidate 裸子串计数（"muse"⊂"museum"）虚增 distinctHits 抬高 rank 与候选置信（`candidates.js:189-219`）。

## 三、v1 已修正的判断（防止按旧结论继续修）

| v1 判断 | 核查结果 |
|---|---|
| 失效 key 的前 5 个调用各自吃满 45s×3 重试窗口 | **错**。确定性 4xx（400/401/403）在网关直接 break 不重试（`llm-gateway.js:139-142`），且在熔断计数递增之前退出 |

| 发现层基本只有 matchScore<40 过滤，漏答默认放行 | **遗漏 60 分门槛**。漏答候选回落自报分后仍须 `fit>=60`（`discover.js:247`） |
| 字段值完全由 LLM 产生 | **表述过度**。渠道存在性/Shopify 价格/币种/官网价格均为代码裁决；准确说法是"多项语义字段主要依赖 LLM，且引用支持性校验缺失" |
| 探测超时按 provider×key 串行相乘 | **不能统一计算**。按错误类型分流：Serper invalid/exhausted 换 key，网络/解析错误直接抛出 |
| （连带收窄）中文查询+gl=us → 恒零命中 | 非代码可证事实；问题是"未检出被升级为确认缺席"，语言不匹配只是放大器 |
| （连带收窄）口碑采集"完全没有超时" | `_getJson` 无应用级超时属实；独立站评论路径已有每路径 10s 超时 |
| （连带作废）"45→90s 消除最坏 +90s、消除双倍计费" | 名义失败预算 138s→181s 反而更长；真实价值是减少 45-90s 任务被中断重试，计费影响待用量数据佐证 |

| （连带作废）"合并翻译与枚举缩短前台" | 二者已并行；真正多余的是扇出 1 被枚举挡住（S2） |

## 五、修订后的修复优先级

原则：**先修"错误状态变成高可信结论"的通道和断掉的链路（不依赖性能数据即可开工），吞吐优化必须以实测为前提，度量前置而不是收尾。**

### P0-A 状态与证据契约（防止错误高可信结论）

| # | 改动 | 位置 | 验收标准 |
|---|---|---|---|
| 1 | 深研探测保留 quota/错误哨兵，与"零命中"分流；负证据收紧为四态（配额不足/探测失败/检出无官方店/确认不存在），默认"未检出" | `enrich.js:224, 289-312` | 超时、配额耗尽、无关引用**都不能产出 verified**（可写单测断言） |

## 六、结语（修订后总述）

当前**已确认**的风险：单项目串行深研、发现阶段扇出被枚举多余阻挡、LLM 超时不覆盖正文、引用支持性校验缺失、配额错误可转成渠道 verified 负证据、自动金标与无效门禁、口碑管线两处接线断裂。它们足以解释慢和不准的**发生机制**；但各因素在生产中的贡献排序未证，修改后的收益（含"耗时降至 1/3"）均为条件估算。实施顺序：**先修 P0-A/P0-B 的状态契约与断链，让埋点真实落盘，再用真实阶段耗时和独立抽检评估 P1 的性能、准确率与覆盖率收益。**

v1 可保留的内核：串行深研与前台多阶段等待累积耗时；字段值与引用内容缺支持性校验，让真实来源承载不受支持的结论。v1 必须废弃的结论见第三节表格——其中"失效 key 重试""首项无 URL 歧义窗口""中文 TIER2 白名单"三项**不应按原判断继续修**。
