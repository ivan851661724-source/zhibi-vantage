# 01 · 前端架构规范（Next.js）

> 状态：**已评审基线**。改动本文档需在提交说明中说明理由。
> 范围：新建的 Next.js 前端服务（代码目录 `web/`）。后端（`app/`）不在本文档范围内，其契约见 [02-API契约.md](./02-API契约.md)。

---

## 1. 技术选型与理由

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | **Next.js（App Router）+ TypeScript** | 文件即路由，天然拆解现有 7 面板单页应用；SSR 能力备而不用（本应用以客户端交互为主） |
| 运行时依赖 | **仅 react / react-dom / next** | 延续项目"依赖极简"纪律；不引入 UI 组件库、不引入状态管理库（见 §5） |
| 样式 | **全局 CSS（迁移现有 `styles.css`）+ CSS Modules** | 98KB 现有样式直接复用，禁止顺带重写视觉；新组件用 Modules 隔离 |
| 数据获取 | **原生 fetch + 自定义 hooks** | 复刻现有 `api()` 封装的行为（token 注入 / JSON 解析 / 错误上抛） |
| 实时推送 | **原生 EventSource（SSE）** | 后端已有 `/api/stream`，协议不变 |
| 包管理 | **pnpm** | 快、省磁盘；lockfile 提交仓库 |

**明确不做的事**：
- 不引入 Redux/Zustand/Jotai —— 全局状态只有 `state`（服务端真相）+ 本地 UI 态，用 Context + hooks 足够。
- 不引入 TanStack Query（一期）—— SSE 推送 + `onPush` 签名比对已解决缓存失效；若二期痛点明确再评估。
- 不做 Tailwind 重构、不改设计稿 —— 迁移期目标是**行为等价**，不是美化。

## 3. 与后端的串联方式（关键决策）

**Next.js 不实现任何业务 API，只做反向代理**：

```ts
// web/next.config.ts
const BACKEND = process.env.BACKEND_URL || 'http://127.0.0.1:3300';
const nextConfig = {
  async rewrites() {
    return [
      { source: '/api/:path*', destination: `${BACKEND}/api/:path*` },
      { source: '/metrics', destination: `${BACKEND}/metrics` },
      { source: '/healthz', destination: `${BACKEND}/healthz` },
    ];
  },
};
export default nextConfig;
```

理由：
1. **免 CORS**：浏览器只 sees 同源，后端零改动。
2. **token 方案不变**：沿用 `Authorization: Bearer <jwt>`（localStorage），不改造成 cookie —— 迁移期行为等价优先；会话安全改造列为二期独立事项。
3. **SSE 可代理**：Next 的 rewrites 透传流式响应；若实测异常，备选方案是前端直连后端域名（需后端开 CORS，仅此一条路）。
4. **部署拓扑**：容器网络内 `BACKEND_URL=http://zhibi-vantage:3300`，见 [03-迁移实施方案.md](./03-迁移实施方案.md) §4。

## 5. 数据流与状态管理

复刻现有模式（单一服务端真相），不做发明：

```
EventSource('/api/stream') ──┐
                             ├─→ useZhibiState() ─→ 签名比对(state.sig) ─→ 重拉 /api/state ─→ 触发面板渲染
轮询兜底(25s ping) ─────────┘
```

约定：
1. **state 只有一份**：来自 `/api/state` 的对象是唯一全局数据源，组件不得私自修改副本（纠错走 POST 端点后等 SSE 通知刷新）。
2. **面板组件均为客户端组件**（`'use client'`）；一期不使用 RSC 取数（后端要求 Bearer 头，客户端持有 token）。
3. **UI 态局部化**：当前 tab 的筛选条件、折叠状态等用 `useState` 留在组件内，禁止上抛到全局。
4. **API 层单一入口**：所有请求必须经 `src/lib/api.ts`，禁止组件内裸写 `fetch`（对齐现 `js/api.js` 的纪律）。

## 6. 单一实现原则的延续

后端在返回 `index.html` 时注入 `window.parsePriceRange`（server.js L19-21），前端与后端共用同一份价格解析。迁移后：

- 将 `app/lib/pricefield.js` 中的 `parsePriceRange` **原样复制**到 `web/src/lib/price.js` 并导出——保持 plain JS、不加类型标注、不改格式（否则无法逐字符比对）；
- 在 `web/package.json` 已内置 check 脚本，比对本份与后端份的函数源码（逐字符）+ 行为冒烟：
  ```json
  { "scripts": { "check:price": "node scripts/check-price-parity.mjs" } }
  ```
- 任一侧修改价格解析，必须双侧同步并通过 parity check，否则 CI 失败。

## 7. 编码约定

1. **TypeScript strict 模式**；`any` 需行内注释说明原因。
2. 文件命名：组件 `PascalCase.tsx`；hooks / 工具 `kebab-case.ts`。
3. 注释语言：中文（与现有代码库一致）；引用后端行为时标注源码位置（如 `server.js L286`）。
4. 错误处理：`api()` 抛出的 `Error` 携带 `status` 字段；401 统一由 `ApiProvider` 捕获后跳转 `/login`。
5. 提交纪律：一个 PR 一个面板（见迁移方案 §3 阶段表），PR 描述须引用本文档章节。

## 8. 验收标准（架构层面）

- [ ] `pnpm build` 零错误零警告（ESLint strict）。
- [ ] 浏览器与后端之间无跨域请求（全部经 Next rewrites）。
- [ ] 断网 30s 内 SSE 自动重连，恢复后 state 签名比对刷新（对齐现有 `startPolling` 行为）。
- [ ] `check:price` 通过（价格解析前后端一致）。
- [ ] Lighthouse 对 / 路由的 JS 传输量 < 300KB gzip（不高于现状 app.js 水平）。
